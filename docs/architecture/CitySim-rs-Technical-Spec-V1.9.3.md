### 0.3 架构演进原则

- 不因局部优化而随意推翻核心架构。

- 不因长期扩展需求而提前引入不必要的复杂度。

- 先验证高风险技术假设，再决定是否冻结相关接口。

- 所有重要架构变化必须有 ADR。

- 所有性能目标必须有可复现测试依据。

## 1. 项目定位与设计目标

### 1.1 项目定位

CitySim-rs 是一个基于 Rust + Bevy 的高性能城市模拟核心引擎。项目重点不是复刻某一商业城市建造游戏，而是构建一套可扩展、可测试、可长期演进的城市模拟基础设施。

核心关注领域：

- 大规模 Agent 模拟。

- 城市道路网络及动态路网。

- 路径搜索与交通流量模拟。

- 确定性模拟与可复现运行。

- 分阶段计算与性能预算控制。

- 可扩展的经济、人口及城市系统。

- 可观察、可调试、可验证的工程架构。

### 1.2 核心设计目标

****性能目标****

- 长期支持大规模 Agent 和城市实体模拟。

- 30 万 Agent 是长期设计目标，不是当前已实现或已验证的性能指标。

- 所有规模目标必须经过固定硬件、固定场景、固定 Tick 数的基准测试。

****确定性目标****

- 在明确的确定性边界内（边界定义见 2.9），保证相同输入和相同模拟条件能够产生可复现的模拟结果。

****可扩展目标****

允许未来增加：

- 更复杂的经济系统。

- 更丰富的 Agent 行为。

- 动态交通模型。

- 多模拟实例。

- 可视化调试工具。

- 服务器端模拟能力。

但不能因为这些潜在需求，提前引入尚无实际用途的复杂架构。

### 1.3 非目标

当前阶段不以以下内容作为核心交付要求：

- 商业游戏级别的完整 UI。

- 多人联机。

- 分布式模拟。

- 大规模网络同步。

- 完整物理沙盒。

- 对特定商业游戏的行为或资产复刻。

- 目标平台构建。

- 关键 API 验证。

- 依赖许可证及安全检查。

Bevy 版本升级应通过 ADR 决策，不应无记录地修改基础依赖。

### 2.2 架构分层

核心设计遵循职责分离原则：

- 模拟核心：管理模拟状态和 Tick 推进。

- Agent 系统：管理 Agent 身份、状态与行为。

- 路网系统：管理道路拓扑、道路修改和路网数据。

- 寻路系统：负责路径搜索与任务调度。

- 交通系统：负责交通流量及相关模型。

- 经济及城市系统：承载后续城市模拟能力。

- 可视化与工具层：展示模拟状态、诊断信息和调试结果。

具体 crate 划分、模块依赖和接口，应在工程目录结构确定时通过架构约束落实。

原则上：

- 模拟核心不能依赖 UI。

- 业务模拟模块不能依赖可视化实现。

- 工具层不能成为模拟状态的唯一管理者。

- 核心数据结构应避免被渲染系统直接控制。

- 模块之间通过明确接口交换数据。

### 2.3 Agent 身份与状态

Agent 身份必须与 ECS Entity 的生命周期解耦。核心身份采用稳定的 AgentId。

设计要求：

- Agent 销毁后，其历史身份不能被其他 Agent 意外复用（存档必须保存 AgentId 分配器高水位，见 EC-03）。

- Agent 身份不能依赖 Bevy Entity 的内部索引。

- Agent 的存档身份必须可以跨进程恢复。

- Agent 身份应支持确定性测试和状态追踪。

- 跨系统引用 Agent 时优先使用稳定身份，而不是直接依赖短生命周期 ECS Entity。

Agent 的数据布局和存储方式应以实际访问模式、内存占用和并行效率为依据，不预先强制所有 Agent 数据采用同一种容器。

### 2.4 数值系统 SimScalar

模拟核心需要统一数值语义。SimScalar 是模拟逻辑使用的数值类型边界，具体底层表示仍需通过 Spike 验证。

候选设计需要评估定点数方案，例如 Q32.32。不能仅根据 Agent 数量决定定点数格式。**SimScalar 的格式（Q32.32、Q24.40 等）取决于 2.10 的参数基线；参数基线未定案前，数值方案和基准测试均无法定案。**

必须测试：

- 城市地图最大坐标范围。

- 最小空间分辨率。

- 速度和加速度范围。

- 经济数值范围。

- 时间累计范围。

- 中间计算所需位宽。

- 长时间积分误差。

- 溢出、饱和和舍入行为。

- 不同平台上的一致性。

Q16.48 不应被简单视为 Q32.32 的升级方案，因为两者的整数范围和小数精度不同。

**格式定案（Spike A 收尾，2026-11-18；2026-11-19 正式裁决：采纳，状态 Accepted）**：2.10 参数基线定案后，Spike A 完成 Python 模拟、Rust 原型（12 测试全过）与定案参数正式核对（9 项硬约束全 PASS），推荐 SimScalar 定案为 Q32.32、舍入"就近舍入，0.5 向远离零取整"、乘除中间值 i128、经济与里程类大整数用独立 i64/u64 整数类型；详见 ADR-NEW-21（数值设计决策，2026-11-19 正式裁决采纳；转 Verified 外围条件：债务 #22 工具链收敛、正式基准、R4 黄金，见 decision-log）。

****数值契约****

- 明确加法、乘法、除法的舍入规则。

- 明确溢出处理方式。

- 禁止依赖未定义或平台相关的隐式行为。

- 关键模拟逻辑不能无记录地混用浮点和定点运算。

- 需要明确哪些系统允许使用浮点数，例如渲染和非权威性展示计算（权威/非权威划分见 2.9）。

****数值契约补充（V1.9.3 新增，状态：Proposed）****

- 权威时间用 u64 tick 计数，不用 SimScalar 做秒累积。证据：Spike A 的 analysis.py 显示 Q32.32 以秒累积约 68 年后溢出。

- dt 由 tick 频率经 from_ratio 一次性派生，并保留其舍入误差，写入黄金测试。

- 乘除的舍入规则采用候选方案"就近舍入，0.5 向远离零取整"；analysis.py 显示截断会让误差单向累积。该结论目前仅来自 Python 模拟，Rust 实现尚未编译验证。

- 经济数值如果超出 SimScalar 的整数范围，应使用独立的整数类型，不强行塞进 SimScalar。

SimScalar 的最终实现应以 Stage 0 Spike 结果和 ADR 决策为准。

### 2.5 路网与路径搜索

路网采用适合高效遍历和批量计算的数据结构。CSR 是当前设计中的核心路网存储方案。路径搜索以 A* 为基础。

设计要求：

- 路网拓扑与动态道路代价分离。

- 路网数据应支持高效批量访问。

- 道路修改不能让正在执行的查询观察到不完整拓扑。

- 路径搜索应有任务预算和调度机制（预算计量必须使用确定性工作量单位，见 2.7）。

- 大规模路径请求不能无约束地占用模拟主线程。

- 路径搜索结果必须能够关联请求、Agent 和路网版本：**每个寻路请求记录 base_network_version，其结果携带同一版本号**，过期结果的处理策略见 EC-01。

具体 CSR 布局、分块粒度、缓存策略和并行策略需要通过性能测试确定。（2026-11-19 更新：CSR 布局已定案——adj_edge_ids 按 (node_id, edge_id) 升序、拓扑事务整表重建原子替换、代价原位更新，见 ADR-NEW-24 决策 1（第二轮评审 Accepted，附条件）；性能实测降为记录项，缓存/并行策略随 Stage 2B。）

### 2.6 动态路网与交通模型

动态路网是核心能力之一。道路拓扑修改与交通动态代价更新必须区分。

- 拓扑修改：影响道路连接关系。

- 动态代价更新：影响路径选择和交通计算。

- 路网版本：用于识别查询所依据的数据版本。

- 路网事务：保证一次完整编辑操作具有明确的逻辑边界。**每个事务必须声明并记录其影响区域**，用于过期寻路结果的相交判断（见 EC-01）。

交通流量模型以 MFD 为候选设计方向。MFD 的适用范围、参数校准、与微观 Agent 交通行为之间的耦合方式，需要通过独立测试确认。不得在缺少验证的情况下将 MFD 的理论表现直接当作实际引擎性能。

### 2.7 LOD 与计算预算

模拟系统应采用分级计算策略。三级 LOD 是当前架构基线中的重要设计：

- 高精度层：执行较完整的模拟逻辑。

- 中精度层：以较低频率或较简化模型更新。

- 低精度层：使用聚合或近似方式减少计算量。

具体层级命名、切换条件和更新频率需要在实现阶段明确。

LOD 层级切换若影响权威模拟结果（中、低精度层的更新频率与简化模型即改变权威状态），其切换条件与切换目标必须为确定性信号（实体属性、确定性工作量单位），禁止墙钟、负载、帧率触发；切换动作须记录进存档与回放输入（V1.9.3 评审修订，对应 ADR-NEW-14）。

****预算即代码****

- 每类高成本系统应有明确预算。

- 预算消耗应有指标记录。

- 超预算行为应进入明确的调度或降级流程。

- 不允许通过无记录地跳过关键模拟步骤来掩盖性能问题。

****预算与降级必须确定性（V1.9.3 新增，状态：Proposed，对应 ADR-NEW-14）****

- 凡是会改变权威模拟状态的预算判断和降级触发，必须基于确定性的工作量单位，例如 A* 节点展开数、队列长度、本 tick 处理的实体数。

- 墙钟耗时、CPU 负载和帧率只用于遥测与告警，不得参与改变权威状态的分支。

- 每个有预算的系统必须声明：计量单位、每 tick 上限、超限行为（延后、分批或降级等级）、对应的诊断事件。

- 如果需要按机器性能调整预算，只能在 tick 边界，通过显式配置变更完成，并且该变更必须写入存档和回放输入。

- 降级的恢复条件同样用工作量单位定义。

验证要求：R2 场景在 1、2、8 线程以及人为注入延迟下运行，摘要必须一致。（执行分层见 EC-11：线程数无关性由 R3 每日构建覆盖，R2 如需覆盖用缩小场景——2026-11-18 评审裁决 #9。）

### 2.8 并行计算与确定性提交

当前架构采用：**并行计算、串行提交。**

适合并行的计算阶段可以并行执行，但影响权威模拟状态的提交必须遵守确定性规则（完整契约见 2.9）。

需要明确：

- 任务输入快照：并行任务只读取 tick 开始时的快照。

- 任务结果排序规则：结果按稳定键（如 AgentId、请求 ID）排序。

- 任务结果字段：寻路结果须携带**所经边 ID 列表**（2026-11-19 增补，依据 ADR-NEW-23 两阶段相交判定：AABB 宽筛后按边 ID 集合窄判，取代整条路径包围盒粗判）。

- 冲突处理规则。

- 提交顺序：排序后串行提交。

- 失败任务处理方式。

- Tick 边界。

Bevy ECS 的系统参数、资源访问和 Query 应继续发挥其访问冲突分析能力。不应为了抽象而让所有系统都接收一个包含全部状态的巨大 &SimulationWorld，从而削弱 ECS 的并行调度优势。

### 2.9 确定性边界（V1.9.3 新增，状态：Proposed，对应 ADR-NEW-15）

本节是全文档中"确定性边界"一词的唯一定义。2.4、2.8、EC-02、EC-05 等章节对该词的引用均以本节为准。

确定性契约共八条：

1. **范围**：首要目标是同一二进制、同一平台上的逐 tick 可复现。跨平台一致性列为 R4 发布前验证项，结论待验证。

2. **权威状态与非权威状态**：权威状态指影响后续模拟结果的数据；渲染、UI、遥测和调试数据属于非权威，不得写回权威状态。

3. **浮点：**权威系统不使用平台 f32/f64 运算。浮点语义必须用位级确定性实现（如软件浮点）并经 ADR 批准；渲染、UI、遥测可用平台浮点。以 f32 为基础的第三方库（如 Rapier）只能用于非权威侧，或经 ADR 豁免后承担权威物理并提供位级确定性证据。

4. **迭代顺序**：权威逻辑不得依赖 HashMap/HashSet 的迭代顺序，也不得假设 Bevy Query 的迭代顺序稳定。需要顺序时，按稳定键（如 AgentId）排序后再处理或提交。

5. **系统顺序**：影响权威状态的系统之间，必须显式声明 before/after 关系，不依赖调度器的偶然顺序。**全序提交与系统执行顺序分开定义**（2026-11-18 外部评审 P1-02 修订）：只对有数据依赖、写冲突或提交顺序要求的系统声明 before/after，无依赖系统保持并行；稳定提交全序键候选 `(phase_id, system_id, request_id, agent_id, local_sequence)`，无 request_id/agent_id 的全局系统提交按 `(phase_id, system_id)` 静态序作为缺省全序。

6. **并行**：并行任务只读取 tick 开始时的快照；结果按稳定键排序后串行提交。

7. **时间**：权威时间是 u64 tick 计数，不读取系统时钟。

8. **外部输入**：玩家命令必须带有生效 tick 编号，并记录下来以便回放。

上述契约应按 EC-12（契约即代码）尽量转为自动检查。候选自动检查包括 clippy.toml 中的 disallowed-types / disallowed-methods 配置（用来禁止 HashMap 和系统时钟，已于 2026-11-18 实测可行，见 docs/benchmarks/clippy-layering-REPORT.md），以及线程数无关测试。

## 3. 工程契约

本章将历版工程契约整合为统一规范。

### 3.1 EC-01：路网修改事务

状态：Proposed，待 Spike 验证

一次玩家完整道路编辑操作应作为逻辑事务。

设计流程：

1. 接收道路编辑请求。

2. 建立事务上下文。

3. 验证修改合法性。

4. 在后台执行必要的数据重建。

5. 完成后进行原子发布。

6. 让后续查询使用新路网版本。

事务必须明确：

- 事务 ID。

- 影响区域。

- 基于的旧路网版本。

- 修改结果。

- 失败原因。

- 发布状态。

设计要求：

- 不允许查询观察到半更新的路网。

- 事务失败不能破坏原有有效路网。

- 用户取消操作必须有明确语义。

- 后台分块重建不能破坏事务整体性。

- 冲突合并规则需要单独验证。

不强制要求所有事务立即实现完整的任意回滚能力。

****过期结果策略（V1.9.3 新增，状态：Proposed，对应 ADR-NEW-17）****

EC-01 保证查询不会看到半更新的路网，但还必须统一规定"基于旧版本算出的结果"如何处理，否则会成为确定性分歧的来源：

- 每个寻路请求记录 base_network_version；其结果携带同一版本号。

- 路网事务必须声明影响区域，并随事务一起记录。

- 影响区域必须同时覆盖拓扑修改与动态代价更新（2.6 区分二者）。

- 当基准版本与当前版本之间存在多笔已发布事务时，相交判断针对该区间内全部事务影响区域的并集进行（聚合规则）。

- 提交结果时，如果当前路网版本不等于基准版本，候选处理策略为：

  - 影响区域与路径不相交：接受结果。

  - 影响区域与路径相交：重新入队重算，受预算和背压控制。

  - 重算次数超过上限：进入前向进展兜底（候选：局部可行路径 / 沿用旧路径有效段 / 标记受阻，由 Spike C 比选后 ADR 定案），不得无限"丢弃-重请求"循环。

- 处理结果不得依赖结果到达的先后顺序；需要顺序时按请求 ID 排序。

- 必须设置重算次数上限，防止在持续修路时出现活锁；并满足前向进展不变量：每个 Agent 必须在有限 tick 内获得可用路径或进入明确定义的受阻状态，不得无限"丢弃-重请求"循环（饥饿）。

- 需要单独定义：Agent 正在行走时，所在道路被删除怎么办（停止、回退还是就近重算）。

默认候选策略为"影响区域相交判断"（状态：Proposed，随 ADR-NEW-17 正式裁决定案），细节由 Spike C 的数据确定。验证方法：Spike C 增加"发布与查询交错"的并发测试，并统计固定场景下过期结果的数量和处理开销。本策略只保证合法性（结果路径所经的边在当前路网中仍存在），不保证最优性（最优性由后续重寻路收敛）。（Spike C 已完成，2026-11-18：原子发布/聚合规则/合法性解耦/前向进展/行走删路比选均已验证，细则定案建议见 ADR-NEW-23，证据见 docs/benchmarks/Spike-C-NetworkTx-REPORT.md，状态：Proposed，待评审裁决。）

### 3.2 EC-02：系统级 RNG 隔离

状态：Proposed，待 Spike 验证

不同模拟系统应拥有相互隔离的随机数流。建议根据以下信息派生系统级随机流：

- 全局随机种子。

- 系统命名空间。

- 系统版本或明确的随机协议版本。

- 必要时的事件标识。

设计目标：

- 一个系统增加随机调用，不应意外改变其他系统的随机序列。

- Agent 随机行为应与无关系统隔离。

- 系统级 RNG 不应依赖线程调度顺序。

- 随机结果应能够在确定性测试中复现（确定性边界定义见 2.9）。

事件驱动随机行为优先考虑事件键派生方式，避免依赖不可控的全局随机调用顺序。

具体 RNG 算法、派生算法和兼容策略必须通过 Spike 与 ADR 确认。若采用"种子 + 系统命名空间 + 事件键"的纯派生方案，存档不需要保存流内部状态；有状态的随机流必须保存其状态（见 EC-03）。

（Spike B 已完成，2026-11-18：双模式协议——纯派生 event_u64 零状态默认 + Stream64 有状态流 16 字节存档——已验证隔离/调度无关/可复现，协议设计见 ADR-NEW-22，状态：Proposed，待评审裁决。）

### 3.3 EC-03：存档兼容

状态：Proposed（V1.9.3 扩充，对应 ADR-NEW-16）

存档采用明确的 Schema 版本管理。最小兼容核心字段候选集在 V1.9.3 中扩充如下：

| 类别 | 字段 | 说明 |
| --- | --- | --- |
| 元数据 | Schema 版本、WorldId、当前 tick（u64）、确定性协议版本 | 读档时先校验版本 |
| 身份 | AgentId、寻路请求 ID、路网事务 ID 三类分配器的高水位（2026-11-19 增补，ADR-NEW-20） | 否则读档后可能复用已销毁的 ID，违反 2.3/ADR-NEW-20，稳定排序键变序使强读档等价失败 |
| 随机数 | 全局种子、RNG 协议版本 | 若系统流由"种子 + 系统命名空间 + 事件键"派生，则不需要保存流内部状态；有状态的随机流必须保存其状态 |
| 路网 | 路网版本号、拓扑、动态代价 | 与路径结果的版本关联 |
| 在途任务 | 寻路请求队列（请求 ID、AgentId、基准路网版本）、未发布的路网事务 | 读档时的处理方式见下方条文 |
| 预算与降级 | 当前降级等级、预算滚动状态、budget_yield_count、stale_recompute_count、每请求等待 tick 与优先级（2026-11-19 增补，ADR-NEW-20 让步机制） | 否则读档后行为会与存档前不同（评审修订注：预算滚动状态的生命周期定义待决；若预算每 tick 重置，tick 边界存档下该字段无意义，保留或删除由 ADR-NEW-14 修订定案，见 decision-log） |
| 校验 | 存档点的 GlobalDigest | 读档后重新计算并比对 |

设计要求：

- 存档格式必须携带 Schema 版本。

- 新增字段应有明确默认值或迁移策略。

- 迁移失败必须可诊断。

- 不兼容字段不能静默丢弃。

- 存档恢复后必须执行一致性检查。

- **存档点只能位于 tick 边界。**

- **在途任务采用"保存并恢复"（2026-11-18 评审修订定案，ADR-NEW-16）：存档包含在途寻路请求队列与未发布路网事务，读档后按原请求 ID、基准路网版本继续处理，不丢弃重新入队。理由：EC-11 读档等价测试（存档读档跑至 M 的摘要 == 直接跑至 M 的摘要）在"丢弃并重新入队"下数学上不可能通过；若将来改为丢弃策略，须把读档等价测试降级为弱形式（两次独立存档-读档运行间摘要一致）并另行 ADR 修订。**

- **读档后必须执行一致性检查，并比对存档中的 GlobalDigest。**

缺少分配器高水位、tick、在途任务和降级状态时，读档后的模拟会与不间断运行的结果分叉，因此上述字段列为最小兼容核心候选集。

**读档等价测试**：在第 N tick 存档、读档，再运行到第 M tick，其摘要必须等于直接运行到第 M tick 的摘要。此测试已列入 R2 门禁（见 EC-11）。该测试为强形式，依赖在途任务"保存并恢复"语义（见上）；若改为"丢弃并重新入队"，须降级为弱形式（两次独立的存档-读档运行之间摘要一致）。

**Step 5 验证记录（2026-11-18，Stage 0）**：存档兼容验证原型 `spikes/save-restore-spike/`（9/9 测试通过）已覆盖本节七类字段完整入档回读、tick 边界存档约束、强读档等价（N=40 存档读档跑至 M=100 == 直接跑至 M）、ID 高水位防复用、有状态随机流回读、篡改拒绝、未知 Schema 可诊断拒绝、尾部多余字节拒绝；证据与读档等价测试模板见 docs/benchmarks/SaveRestore-Validation-REPORT.md。当前状态摘要为 FNV-1a 占位实现，GlobalDigest 定案（ADR-NEW-19，Proposed）后在唯一替换点升级为 BLAKE3-256。正式存档序列化格式仍属待决事项（decision-log 债务登记 #11）。

永久兼容边界尚未最终确定，需要结合实际存档结构进行 ADR 决策。

### 3.4 EC-04：降级机制与用户可见性

状态：Proposed（V1.9.3 补充确定性触发约束，对应 ADR-NEW-14）

模拟系统可以在确定性工作量预算超限时执行降级（见 2.7 / ADR-NEW-14；2026-11-18 评审修订：降级触发不得使用墙钟、资源压力或帧率等非确定性信号）。当前采用三级设计方向：

| 等级 | 语义 | 用户可见性 |
| --- | --- | --- |
| L1 | 轻度降级 | 记录指标，通常不需要强提示 |
| L2 | 明显降级 | 提供诊断信息，必要时提示 |
| L3 | 严重降级 | 必须让用户能够识别影响 |

降级行为必须：

- 有明确触发条件。

- 有系统级记录。

- 有恢复条件。

- 不掩盖模拟错误。

- 不静默改变重要模拟语义。

**触发信号约束（V1.9.3 新增）**：降级触发和恢复条件必须遵守 2.7 的确定性预算规则——只使用确定性工作量单位（如队列长度、节点展开数、本 tick 处理实体数），墙钟耗时、CPU 负载和帧率只用于遥测与告警，不得参与改变权威状态的降级分支。按机器性能调整预算只能在 tick 边界通过显式配置变更完成，并写入存档和回放输入。

具体哪些系统允许 L1、L2 或 L3 降级，应分别定义。性能压力的正确体现是"工作量上限内的延后"，而不是"自动变快"。

### 3.5 EC-05：确定性回归体系

状态：Accepted，具体实现待验证

确定性回归应覆盖：

- 固定输入。

- 固定随机种子。

- 固定 Tick 数。

- 固定模拟配置。

- 关键模块摘要。

- 全局摘要。

- 首次分歧定位。

GlobalDigest 用于描述指定确定性边界内（边界定义见 2.9）的权威模拟状态。

摘要设计必须明确：

- 纳入哪些状态（权威状态，划分标准见 2.9）。

- 排除哪些非权威数据（渲染、UI、遥测、调试数据）。

- 序列化顺序。

- 哈希算法及版本。

- 浮点数据处理规则（权威状态不含浮点，见 2.9 第 3 条）。

- 跨平台一致性要求（列为 R4 发布前验证项）。

不能仅因为两个运行的最终画面相似，就认定模拟结果确定。

**线程数无关性**：确定性回归应包含在 1、2、8 线程及人为注入延迟下运行同一 R2 场景、摘要一致的测试（对应 ADR-NEW-14 验证方法）。（执行分层见 EC-11：R2 门禁只跑单线程基准与读档等价，线程数无关性在 R3 每日构建执行。）

## 4. 工程落地与质量保障

### 4.1 EC-06：Stage 0 风险优先级

状态：Accepted

Stage 0 不应平均分配精力，而应优先解决高风险技术假设。

****第一梯队：最高风险****

- SimScalar 数值方案（前提：先补齐 2.10 参数基线，它直接决定 Spike A 能否出结论）。

- 系统级 RNG 隔离。

- 路网事务与原子发布（含过期结果策略，见 EC-01）。

这些项目会影响底层数据语义和后续架构接口，应优先 Spike。

****第二梯队：工程可靠性****

- 存档迁移（含 EC-03 扩充字段与读档等价测试）。

- 降级机制（含确定性触发约束）。

- 确定性回归（含 2.9 契约的自动检查候选）。

****第三梯队：可观测性与长期验证****

- 调试面板。

- 指标导出。

- 长时间运行测试。

Stage 0 退出条件不是"完成所有功能"，而是高风险假设有足够证据支持设计决策。

### 4.2 EC-07：统一测试基础设施

状态：Proposed

建议建立可复用的测试支持模块，例如 sim-test-support。

建议组织：

- fixtures：测试数据和场景。

- deterministic：确定性黄金测试（含读档等价测试模板）。

- property：属性测试。

- benchmark：基准测试模板。

- assertions：模拟状态断言。

测试体系需要覆盖：

**单元测试**：验证独立算法、数据结构和数值运算。

**属性测试**：验证不变量，例如：

- 路网边引用合法。

- Agent 身份不重复。

- 事务发布前后状态有效。

- 数值运算遵守预期边界。

- 过期寻路结果的重算次数不超过上限。

**集成测试**：验证多个模块组合后的行为。

**确定性测试**：固定输入和种子，重复运行并比较摘要；覆盖线程数无关性和读档等价性。

**基准测试**：固定场景、硬件、构建模式和 Tick 数，记录运行耗时与内存占用。

测试支持模块本身不应成为核心运行时依赖。

**Step 6 验证记录（2026-11-18，Stage 0）**：统一测试基础设施原型 `crates/sim-test-support/`（9/9 测试通过）已按上文组织落地五模块：fixtures（reference-100k / r2-gate-10k / smoke-1k 三档确定性场景 + 稳定序网格路网生成器）、deterministic（读档等价测试模板：strong_readback_digests 强形式 / weak_form_digests 弱形式 / repeat_run_digests 黄金复现，通用 SimHarness 接口，来源 docs/benchmarks/SaveRestore-Validation-REPORT.md）、property（五项不变量判定函数）、benchmark（基准记录模板）、assertions（模拟状态断言）。crate 文档与 Cargo.toml 均注明"仅允许 dev-dependency 引入，不得进入权威模拟 crate"。

### 4.3 EC-08：统一错误分层

状态：Proposed

错误分为三类：

| 类型 | 处理语义 |
| --- | --- |
| Fatal | 当前模拟实例无法安全继续，需要终止该实例或安全停止 |
| Recoverable | 可以通过兜底逻辑恢复，但必须记录 |
| Diagnostic | 仅用于诊断、调试或状态提示 |

Fatal 不意味着必须杀死整个进程。

错误上下文建议包含 SimErrorContext：

- system_id

- error_code

- simulation_tick

- entity_id

- world_id

各模块保留自己的错误类型，再转换为统一诊断事件。不建议创建一个包含所有模块错误的大型全局枚举。

### 4.4 EC-09：对象池规范

状态：Proposed，有条件采纳

对象池可以用于经过测量后确认存在分配开销的热点。

统一规范应关注：

- 申请。

- 归还。

- 重置。

- 所有权。

- 容量限制。

- 线程安全。

- 池命中率。

- 分配和回收指标。

可以采用线程本地池与全局兜底池的组合，但不是强制要求。不应为了统一接口而把原本高效的连续内存分配改造成复杂对象池。对象池的引入必须由基准测试证明收益。

### 4.5 EC-10：多世界边界

状态：Proposed，有条件采纳

预留 SimulationContext 和 WorldId 的边界。目标是让不同模拟实例的状态能够明确归属。

未来可支持：

- 并行测试。

- 规划预览。

- 对比模拟。

- 多城市模拟实例。

- 服务器端模拟。

当前不要求实现第二套 ECS，也不要求立即支持多人、网络同步或分布式模拟。

Bevy ECS 仍负责其擅长的实体、组件和系统调度工作。多世界抽象不能削弱 ECS 的访问分析和并行能力。

### 4.6 EC-11：确定性 CI 合并门禁

状态：Accepted，具体阈值待验证

建议将测试分为以下层级：

| 层级 | 内容 | 执行频率 |
| --- | --- | --- |
| R0 | 单元测试、属性测试 | 每次相关提交 |
| R1 | 模块集成测试 | 每次 PR |
| R2 | 固定小规模确定性场景 | PR 合并门禁 |
| R3 | 大规模和长时间测试 | 每日构建 |
| R4 | 跨平台验证 | 发布前 |

R2 初始建议场景：

- 10,000 Agent。

- 1,000 Tick。

- 固定输入。

- 固定随机种子。

- 固定模拟配置。

- 比较确定性摘要。

确定性覆盖分层（V1.9.3 新增；2026-11-18 评审修订按门禁成本分层）：

- **读档等价测试（R2 合并门禁）：**第 N tick 存档、读档后运行到第 M tick，摘要必须等于直接运行到第 M tick（ADR-NEW-16，强形式，依赖"保存并恢复"语义）。

- **线程数无关性（R3 每日构建，不进入 R2 门禁；R2 如需覆盖用缩小场景）：同一场景在 1、2、8 线程及人为注入延迟下运行，摘要必须一致（ADR-NEW-14）。分层理由：叠加读档等价后 R2 每次 PR 需 6 次以上全场景运行，门禁耗时不可接受；实测耗时记录于 docs/benchmarks/ 后复核。**

该场景是初始测试目标，不是已达成的性能指标。

必须实测：

- 总运行耗时。

- 内存峰值。

- 每 Tick 耗时。

- 摘要计算开销。

- 失败时的首次分歧位置。

黄金测试基准不得自动覆盖。如果算法优化导致摘要变化，必须：

- 说明变化原因。

- 提供新旧行为差异。

- 证明变化符合预期。

- 经过人工审核后更新基准。

**Step 7 验证记录（2026-11-18，Stage 0）**：基础 CI 骨架 `.github/workflows/ci.yml` 已建立——R0/R1 门禁=cargo test 矩阵（五 crate）、EC-12 门禁=clippy -D warnings 矩阵（四个权威侧 crate）、R2 确定性场景为占位 job（启用条件：模拟核心 + GlobalDigest（ADR-NEW-19）+ R2 场景 fixture 就绪）。门禁耗时实测数据待模拟核心就绪后按 R2/R3 分层记录于 docs/benchmarks/。

- 禁止不合理的 crate 依赖方向。

- Bevy 系统调度冲突审查（落实 2.9 第 5 条：权威系统必须显式声明 before/after）。

各 ADR 要点摘要：

****ADR-NEW-14：预算与降级必须确定性****

- 问题：如果按墙钟耗时触发降级，同样的输入在不同机器上会走不同分支，GlobalDigest 无法复现。

- 决策：权威预算只使用确定性工作量单位；墙钟时间只做遥测。

- 替代方案：按墙钟时间自适应（性能最好，但直接破坏确定性）；固定 tick 数上限（简单，但不能适应不同系统的成本差异）。

- 影响：每个高成本系统要先定义自己的计量单位；性能压力体现为"工作量上限内的延后"，而不是"自动变快"。

- 验证方法：线程数无关性（同一场景在 1、2、8 线程及人为注入延迟下运行，摘要必须一致）在 R3 每日构建执行；R2 合并门禁只跑单线程基准与读档等价测试，R2 如需覆盖用缩小场景（2026-11-18 评审修订分层）。

****ADR-NEW-15：确定性边界定义****

- 问题：多个章节使用"确定性边界"一词但文档没有定义，无法判断代码是否违规，R2 门禁不知道该保护什么。

- 决策：采用 2.9 的八条作为确定性契约，并按 EC-12 尽量转为自动检查。

- 替代方案：只依靠代码评审（容易漏）；整个引擎使用统一的确定性容器（成本高，也可能削弱 ECS 的并行能力）。

- 影响：权威代码对集合类型和迭代方式有约束；需要为排序提交预留开销。

- 验证方法：clippy.toml 的 disallowed-types / disallowed-methods 配置（禁止 HashMap 和系统时钟，已于 2026-11-18 实测可行，见 docs/benchmarks/clippy-layering-REPORT.md），以及线程数无关测试。配置按 crate 分层：权威模拟 crate 禁用，渲染、UI、遥测 crate 不受限（2026-11-18 评审修订）。

****ADR-NEW-16：存档最小集合扩充****

- 问题：缺少分配器高水位、tick、在途任务和降级状态时，读档后的模拟会与不间断运行的结果分叉。

- 决策：采用 EC-03 扩充表作为最小兼容核心候选集，并增加读档等价测试。在途任务采用"保存并恢复"（2026-11-18 评审修订定案，与读档等价测试强形式绑定）。

- 替代方案：存档只保存世界快照、读档时重建所有派生状态（体积小，但重建结果难以保证与原运行一致）。

- 影响：存档格式变大；Schema 迁移需要覆盖新增字段。

- 验证方法：读档等价测试（第 N tick 存档、读档后运行到第 M tick，摘要等于直接运行到第 M tick），已列入 R2 门禁。（强形式，依赖在途任务"保存并恢复"语义；若改为"丢弃并重新入队"，须降级为弱形式（两次独立的存档-读档运行之间摘要一致）并另行 ADR 修订。）

****ADR-NEW-17：路网事务的过期结果策略****

- 问题：不同处理方式会产生不同的 Agent 行为，必须有统一契约，否则会成为确定性分歧的来源。

- 决策：以"影响区域相交判断"为默认策略，细节由 Spike C 的数据确定。2026-11-18 评审修订补充：相交判断按基准版本与当前版本之间全部事务影响区域的并集聚合；影响区域覆盖拓扑修改与动态代价更新；只保证合法性不保证最优性；重算超限进入前向进展兜底（候选：局部可行路径 / 沿用旧路径有效段 / 标记受阻，Spike C 比选定案）。

- 替代方案：全部重算（简单，但在频繁修路时负载高）；全部接受（可能让 Agent 走已不存在的边）；提交时逐边校验（精确，但成本随路径长度增长）。

- 影响：事务需要记录影响区域；寻路结果需要保存路径经过的区域信息。

- 验证方法：Spike C 增加"发布与查询交错"的并发测试，并统计固定场景下过期结果的数量和处理开销。

****ADR-NEW-18：仿真参数基线与数值契约补充****

- 问题：没有参数基线，数值方案和基准测试都无法定案，也无法比较不同人的测试结果。

- 决策：先固定 2.10 参数基线，再据此确定 SimScalar 格式。

- 替代方案：先选定格式再回头约束需求（容易在后期发现范围不够）。

- 影响：Spike A 的结论依赖参数基线表；参数变更需要走 ADR。

- 验证方法：用确定下来的参数重跑 analysis.py，并在 Rust 中做对应的范围与漂移测试。实验脚本与运行输出入仓 docs/benchmarks/ 保证可复现（2026-11-18 评审修订；analysis.py 及其输出已于 2026-11-18 入仓 docs/benchmarks/）。

注意：以上 ADR 编号是整合后的索引。正式进入仓库后，应为每个 ADR 建立独立文件，并保留决策历史。

## 10. 最终工程原则

CitySim-rs 的核心目标不是尽可能早地堆叠功能，而是建立一个能够长期演进的模拟引擎。

必须坚持：

- 架构目标不等于实现结果。

- 实现结果不等于验证通过。

- 性能目标不等于性能证据。

- 并行化不能以破坏确定性为代价。

- **权威预算与降级触发只能使用确定性工作量单位，墙钟时间只做遥测。**

- **确定性以 2.9 的边界定义为准，权威状态与非权威状态严格分离。**

- 抽象不能以削弱 Bevy ECS 能力为代价。

- 扩展性不能成为过度设计的理由。

- 所有高风险设计都必须先验证再冻结。

- 重要决策必须有 ADR 和可追溯记录。

- CI 必须保护已验证的工程契约。

- 对外宣传只描述已经实现并有证据支持的能力。

V1.9.3 的核心意义：在 V1.9.2 的工程规范基础上，把"确定性"从散落的口号收敛为可检查、可测试、可门禁的契约——定义确定性边界（2.9）、约束预算与降级信号（2.7 / EC-04）、扩充存档最小集合（EC-03）、统一过期路网结果策略（EC-01）、补齐数值方案的前提条件（2.10）。

当前版本仍为公开评审稿。完成参数基线定案、三个核心 Spike、建立可复现测试基础设施并通过关键架构评审后，再考虑发布架构冻结版本。
