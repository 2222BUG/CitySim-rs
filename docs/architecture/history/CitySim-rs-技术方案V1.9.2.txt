0.3 架构演进原则


不因局部优化而随意推翻核心架构。

不因长期扩展需求而提前引入不必要的复杂度。

先验证高风险技术假设，再决定是否冻结相关接口。

核心功能与扩展功能明确分离。

所有重要架构变化必须有 ADR。

所有性能目标必须有可复现测试依据。





1. 项目定位与设计目标

1.1 项目定位

CitySim-rs 是一个基于 Rust + Bevy 的高性能城市模拟核心引擎。

项目重点不是复刻某一商业城市建造游戏，而是构建一套可扩展、可测试、可长期演进的城市模拟基础设施。

核心关注领域：


大规模 Agent 模拟。

城市道路网络及动态路网。

路径搜索与交通流量模拟。

确定性模拟与可复现运行。

分阶段计算与性能预算控制。

可扩展的经济、人口及城市系统。

可观察、可调试、可验证的工程架构。



1.2 核心设计目标

性能目标

长期支持大规模 Agent 和城市实体模拟。

30 万 Agent 是长期设计目标，不是当前已实现或已验证的性能指标。

所有规模目标必须经过固定硬件、固定场景、固定 Tick 数的基准测试。

确定性目标

在明确的确定性边界内，保证相同输入和相同模拟条件能够产生可复现的模拟结果。

可扩展目标

允许未来增加：


更复杂的经济系统。

更丰富的 Agent 行为。

动态交通模型。

多模拟实例。

可视化调试工具。

服务器端模拟能力。



但不能因为这些潜在需求，提前引入尚无实际用途的复杂架构。

1.3 非目标

当前阶段不以以下内容作为核心交付要求：


商业游戏级别的完整 UI。

多人联机。

分布式模拟。

大规模网络同步。

完整物理沙盒。

对特定商业游戏的行为或资产复刻。

2.2 架构分层

核心设计遵循职责分离原则：


模拟核心：管理模拟状态和 Tick 推进。

Agent 系统：管理 Agent 身份、状态与行为。

路网系统：管理道路拓扑、道路修改和路网数据。

寻路系统：负责路径搜索与任务调度。

交通系统：负责交通流量及相关模型。

经济及城市系统：承载后续城市模拟能力。

可视化与工具层：展示模拟状态、诊断信息和调试结果。



具体 crate 划分、模块依赖和接口，应在工程目录结构确定时通过架构约束落实。

原则上：


模拟核心不能依赖 UI。

业务模拟模块不能依赖可视化实现。

工具层不能成为模拟状态的唯一管理者。

核心数据结构应避免被渲染系统直接控制。

模块之间通过明确接口交换数据。



2.3 Agent 身份与状态

Agent 身份必须与 ECS Entity 的生命周期解耦。

核心身份采用稳定的 AgentId。

设计要求：


Agent 销毁后，其历史身份不能被其他 Agent 意外复用。

Agent 身份不能依赖 Bevy Entity 的内部索引。

Agent 的存档身份必须可以跨进程恢复。

Agent 身份应支持确定性测试和状态追踪。

跨系统引用 Agent 时优先使用稳定身份，而不是直接依赖短生命周期 ECS Entity。



Agent 的数据布局和存储方式应以实际访问模式、内存占用和并行效率为依据，不预先强制所有 Agent 数据采用同一种容器。

2.4 数值系统 SimScalar

模拟核心需要统一数值语义。

SimScalar 是模拟逻辑使用的数值类型边界，具体底层表示仍需通过 Spike 验证。

候选设计需要评估定点数方案，例如 Q32.32。

不能仅根据 Agent 数量决定定点数格式。

必须测试：


城市地图最大坐标范围。

最小空间分辨率。

速度和加速度范围。

经济数值范围。

时间累计范围。

中间计算所需位宽。

长时间积分误差。

溢出、饱和和舍入行为。

不同平台上的一致性。



Q16.48 不应被简单视为 Q32.32 的升级方案，因为两者的整数范围和小数精度不同。

数值契约


明确加法、乘法、除法的舍入规则。

明确溢出处理方式。

禁止依赖未定义或平台相关的隐式行为。

关键模拟逻辑不能无记录地混用浮点和定点运算。

需要明确哪些系统允许使用浮点数，例如渲染和非权威性展示计算。



SimScalar 的最终实现应以 Stage 0 Spike 结果和 ADR 决策为准。

2.5 路网与路径搜索

路网采用适合高效遍历和批量计算的数据结构。

CSR 是当前设计中的核心路网存储方案。

路径搜索以 A* 为基础。

设计要求：


路网拓扑与动态道路代价分离。

路网数据应支持高效批量访问。

道路修改不能让正在执行的查询观察到不完整拓扑。

路径搜索应有任务预算和调度机制。

大规模路径请求不能无约束地占用模拟主线程。

路径搜索结果必须能够关联请求、Agent 和路网版本。



具体 CSR 布局、分块粒度、缓存策略和并行策略需要通过性能测试确定。

2.6 动态路网与交通模型

动态路网是核心能力之一。

道路拓扑修改与交通动态代价更新必须区分。


拓扑修改：影响道路连接关系。

动态代价更新：影响路径选择和交通计算。

路网版本：用于识别查询所依据的数据版本。

路网事务：保证一次完整编辑操作具有明确的逻辑边界。



交通流量模型以 MFD 为候选设计方向。

MFD 的适用范围、参数校准、与微观 Agent 交通行为之间的耦合方式，需要通过独立测试确认。

不得在缺少验证的情况下将 MFD 的理论表现直接当作实际引擎性能。

2.7 LOD 与计算预算

模拟系统应采用分级计算策略。

三级 LOD 是当前架构基线中的重要设计：


高精度层：执行较完整的模拟逻辑。

中精度层：以较低频率或较简化模型更新。

低精度层：使用聚合或近似方式减少计算量。



具体层级命名、切换条件和更新频率需要在实现阶段明确。

预算即代码：


每类高成本系统应有明确预算。

预算消耗应有指标记录。

超预算行为应进入明确的调度或降级流程。

不允许通过无记录地跳过关键模拟步骤来掩盖性能问题。



2.8 并行计算与确定性提交

当前架构采用：

并行计算、串行提交。

适合并行的计算阶段可以并行执行，但影响权威模拟状态的提交必须遵守确定性规则。

需要明确：


任务输入快照。

任务结果排序规则。

冲突处理规则。

提交顺序。

失败任务处理方式。

Tick 边界。



Bevy ECS 的系统参数、资源访问和 Query 应继续发挥其访问冲突分析能力。

不应为了抽象而让所有系统都接收一个包含全部状态的巨大 &SimulationWorld，从而削弱 ECS 的并行调度优势。



3. 工程契约

本章将 V1.9.1 中的工程契约整合为统一规范。

3.1 EC-01：路网修改事务

状态：Proposed，待 Spike 验证

一次玩家完整道路编辑操作应作为逻辑事务。

设计流程：


接收道路编辑请求。

建立事务上下文。

验证修改合法性。

在后台执行必要的数据重建。

完成后进行原子发布。

让后续查询使用新路网版本。



事务必须明确：


事务 ID。

影响区域。

基于的旧路网版本。

修改结果。

失败原因。

发布状态。



设计要求：


不允许查询观察到半更新的路网。

事务失败不能破坏原有有效路网。

用户取消操作必须有明确语义。

后台分块重建不能破坏事务整体性。

冲突合并规则需要单独验证。



不强制要求所有事务立即实现完整的任意回滚能力。

3.2 EC-02：系统级 RNG 隔离

状态：Proposed，待 Spike 验证

不同模拟系统应拥有相互隔离的随机数流。

建议根据以下信息派生系统级随机流：


全局随机种子。

系统命名空间。

系统版本或明确的随机协议版本。

必要时的事件标识。



设计目标：


一个系统增加随机调用，不应意外改变其他系统的随机序列。

Agent 随机行为应与无关系统隔离。

系统级 RNG 不应依赖线程调度顺序。

随机结果应能够在确定性测试中复现。



事件驱动随机行为优先考虑事件键派生方式，避免依赖不可控的全局随机调用顺序。

具体 RNG 算法、派生算法和兼容策略必须通过 Spike 与 ADR 确认。

3.3 EC-03：存档兼容

状态：Proposed

存档采用明确的 Schema 版本管理。

需要确定最小兼容核心字段候选集：


AgentId。

位置。

核心状态语义。

必要的模拟世界标识。

恢复模拟所必需的其他权威数据。



设计要求：


存档格式必须携带 Schema 版本。

新增字段应有明确默认值或迁移策略。

迁移失败必须可诊断。

不兼容字段不能静默丢弃。

存档恢复后必须执行一致性检查。



永久兼容边界尚未最终确定，需要结合实际存档结构进行 ADR 决策。

3.4 EC-04：降级机制与用户可见性

状态：Proposed

模拟系统可以在预算不足或资源压力较高时执行降级。

当前采用三级设计方向：




等级

语义

用户可见性







L1

轻度降级

记录指标，通常不需要强提示




L2

明显降级

提供诊断信息，必要时提示




L3

严重降级

必须让用户能够识别影响







降级行为必须：


有明确触发条件。

有系统级记录。

有恢复条件。

不掩盖模拟错误。

不静默改变重要模拟语义。



具体哪些系统允许 L1、L2 或 L3 降级，应分别定义。

3.5 EC-05：确定性回归体系

状态：Accepted，具体实现待验证

确定性回归应覆盖：


固定输入。

固定随机种子。

固定 Tick 数。

固定模拟配置。

关键模块摘要。

全局摘要。

首次分歧定位。



GlobalDigest 用于描述指定确定性边界内的权威模拟状态。

摘要设计必须明确：


纳入哪些状态。

排除哪些非权威数据。

序列化顺序。

哈希算法及版本。

浮点数据处理规则。

跨平台一致性要求。



不能仅因为两个运行的最终画面相似，就认定模拟结果确定。



4. 工程落地与质量保障

4.1 EC-06：Stage 0 风险优先级

状态：Accepted

Stage 0 不应平均分配精力，而应优先解决高风险技术假设。

第一梯队：最高风险


SimScalar 数值方案。

系统级 RNG 隔离。

路网事务与原子发布。



这些项目会影响底层数据语义和后续架构接口，应优先 Spike。

第二梯队：工程可靠性


存档迁移。

降级机制。

确定性回归。



第三梯队：可观测性与长期验证


调试面板。

指标导出。

长时间运行测试。



Stage 0 退出条件不是“完成所有功能”，而是高风险假设有足够证据支持设计决策。

4.2 EC-07：统一测试基础设施

状态：Proposed

建议建立可复用的测试支持模块，例如：

sim-test-support

建议组织：


fixtures：测试数据和场景。

deterministic：确定性黄金测试。

property：属性测试。

benchmark：基准测试模板。

assertions：模拟状态断言。



测试体系需要覆盖：

单元测试

验证独立算法、数据结构和数值运算。

属性测试

验证不变量，例如：


路网边引用合法。

Agent 身份不重复。

事务发布前后状态有效。

数值运算遵守预期边界。



集成测试

验证多个模块组合后的行为。

确定性测试

固定输入和种子，重复运行并比较摘要。

基准测试

固定场景、硬件、构建模式和 Tick 数，记录运行耗时与内存占用。

测试支持模块本身不应成为核心运行时依赖。

4.3 EC-08：统一错误分层

状态：Proposed

错误分为三类：




类型

处理语义







Fatal

当前模拟实例无法安全继续，需要终止该实例或安全停止




Recoverable

可以通过兜底逻辑恢复，但必须记录




Diagnostic

仅用于诊断、调试或状态提示







Fatal 不意味着必须杀死整个进程。

错误上下文建议包含：

SimErrorContext


system_id

error_code

simulation_tick

entity_id

world_id



各模块保留自己的错误类型，再转换为统一诊断事件。

不建议创建一个包含所有模块错误的大型全局枚举。

4.4 EC-09：对象池规范

状态：Proposed，有条件采纳

对象池可以用于经过测量后确认存在分配开销的热点。

统一规范应关注：


申请。

归还。

重置。

所有权。

容量限制。

线程安全。

池命中率。

分配和回收指标。



可以采用线程本地池与全局兜底池的组合，但不是强制要求。

不应为了统一接口而把原本高效的连续内存分配改造成复杂对象池。

对象池的引入必须由基准测试证明收益。

4.5 EC-10：多世界边界

状态：Proposed，有条件采纳

预留 SimulationContext 和 WorldId 的边界。

目标是让不同模拟实例的状态能够明确归属。

未来可支持：


并行测试。

规划预览。

对比模拟。

多城市模拟实例。

服务器端模拟。



当前不要求实现第二套 ECS，也不要求立即支持多人、网络同步或分布式模拟。

Bevy ECS 仍负责其擅长的实体、组件和系统调度工作。

多世界抽象不能削弱 ECS 的访问分析和并行能力。

1,000 Tick。

固定输入。

固定随机种子。

固定模拟配置。

比较确定性摘要。

黄金测试基准不得自动覆盖。

如果算法优化导致摘要变化，必须：


说明变化原因。

提供新旧行为差异。

证明变化符合预期。

经过人工审核后更新基准。



4.7 EC-12：契约即代码

状态：Proposed

架构规则应尽可能转化为自动检查。

候选检查：


Rust 类型系统约束。

Clippy。

依赖层级检查。

禁止不合理的 crate 依赖方向。

Bevy 系统调度冲突审查。

关键数值类型使用约束。

CI 确定性门禁。

依赖许可证与安全检查。



cargo-deny 可用于依赖、许可证和安全策略管理，但不能单独证明项目 crate 架构层级正确。

依赖结构检查需要额外的规则或脚本。

4.8 EC-13：最小可视化 Demo

状态：Proposed

Stage 2A 完成后，建议提供一个最小可视化 Demo。

初始目标：


10,000 Agent 场景。

能够观察 Agent 的基本行为。

能够展示道路网络。

能够观察路径搜索结果。

能够查看基本模拟指标。

能够复现固定场景。



Demo 的主要目的：


验证核心架构能够实际运行。

为社区提供可见的工程入口。

降低外部开发者理解和贡献的成本。



Demo 的性能表现必须通过实测报告说明，不得提前承诺帧率或运行耗时。

7. 第三方评审与验证要求

V1.9.2 仍然是公开评审稿，不应宣布架构冻结。

后续评审应集中于以下问题：


SimScalar 的数值格式、位宽和误差是否满足长期模拟要求？

系统级 RNG 如何保证隔离、跨平台一致性及版本兼容？

路网事务如何保证原子发布，并处理并发修改冲突？

CSR 分块和 A* 调度是否适合目标规模？

确定性摘要应覆盖哪些权威状态？

多世界抽象是否会削弱 Bevy ECS 的调度能力？

对象池是否确实能在目标负载下带来性能收益？

10,000 Agent × 1,000 Tick 的测试如何控制运行时间和资源占用？

Demo 应展示哪些真实完成的能力？

各项技术依赖是否有可复现的编译和兼容性证据？



外部评审建议必须经过工程裁决，不应直接全部纳入。

建议使用以下裁决：


采纳。

有条件采纳。

拒绝。

延后。



每项裁决应记录理由和验证条件。

10. 最终工程原则

CitySim-rs 的核心目标不是尽可能早地堆叠功能，而是建立一个能够长期演进的模拟引擎。

必须坚持：


架构目标不等于实现结果。

实现结果不等于验证通过。

性能目标不等于性能证据。

并行化不能以破坏确定性为代价。

抽象不能以削弱 Bevy ECS 能力为代价。

扩展性不能成为过度设计的理由。

所有高风险设计都必须先验证再冻结。

重要决策必须有 ADR 和可追溯记录。

CI 必须保护已验证的工程契约。

对外宣传只描述已经实现并有证据支持的能力。



V1.9.2 的核心意义：将 CitySim-rs 从一份架构构想推进为一套可以被实现、测试、审查和持续演进的工程规范。

当前版本仍为公开评审稿。完成三个核心 Spike、建立可复现测试基础设施并通过关键架构评审后，再考虑发布架构冻结版本。
