# ADR-NEW-22：系统级 RNG 协议（Spike B 数值/协议设计决策）

- 编号：ADR-NEW-22（暂定编号，正式入仓时按仓库 ADR 序列重新编号并保留映射）
- 状态：Proposed
- 日期：2026-11-18
- 关联主文档章节：EC-02（3.2）、EC-03（3.3）、2.9（确定性边界）、Spike B、Stage 0
- 来源：Spike B（Step 3，2026-11-18）；审计债务 #4（RNG 算法/派生键编码/协议 bump 策略）

## 背景

EC-02 要求系统级随机流相互隔离、调度无关、可复现，且"具体 RNG 算法、派生算法和兼容策略必须通过 Spike 与 ADR 确认"。Spike B 原型（spikes/rng-spike，9 测试全过）验证了双模式设计并比较了三个候选算法。

## 问题

RNG 算法、派生键编码、协议版本化与存档口径如何定案？

## 决策

1. **双模式随机源**：
   - **纯派生模式（默认，事件驱动行为）**：`event_u64(global_seed, namespace, event_key, draw_index)`——每次抽取独立由（全局种子、系统命名空间、事件键、抽取序号）派生，零流状态、调度无关、存档零负担。
   - **有状态流模式（顺序消费场景）**：`Stream64{seed, counter}`（计数器式），存档 16 字节/流（seed+counter），读档后续列一致。
2. **算法（协议 v1）**：SplitMix64 为派生混合与顺序流的基础算法（0.59 ns/draw，8 B 状态）；备选 xoshiro256\*\*（0.73 ns）、PCG64（1.14 ns）。Spike 结论：三候选速度均远低于预算，选择以简洁与状态最小为先。
3. **派生键编码（协议 v1）**：namespace 的 UTF-8 字节 → FNV-1a 64；`mix(global_seed ^ ns_hash, event_key)` 两轮 SplitMix64 混合；抽取序号以独立常数混淆后参与混合。编码顺序、常数、输出映射全部属协议内容，变更必须 bump 版本。
4. **协议版本化**：`RNG_PROTOCOL_VERSION: u16 = 1` 随全局种子入 EC-03 存档；任何算法/编码/映射变更必须 bump 版本并修订本 ADR；读档时版本不符的处理策略随 EC-03 兼容矩阵（审计债务 #12）定案。
5. **存档口径**：纯派生流不保存任何流状态（EC-03 随机数行既定条文落实）；有状态流必须保存（seed, counter）或完整内部状态。

## 考虑过的替代方案

| 方案 | 评价 |
| --- | --- |
| 全局单一 RNG 按调用顺序消费 | 一个系统多抽一次即改变其他系统序列，违反 EC-02 设计目标，否决 |
| 全部有状态流（每系统/每 Agent 一条） | 存档负担大（每流 16~32 B × 流数量），且调度交错仍需按流隔离；保留为顺序消费场景的补充 |
| xoshiro256\*\* 为主 | 状态 32 B、跳跃函数生态好，但本阶段无跳跃需求，简洁性不如 SplitMix64，备选 |
| PCG64 为主 | 统计质量口碑最好，但 u128 状态与 2 倍速度劣势在 10 万 Agent 场景无收益，备选 |

## 影响

- EC-02 从"Proposed，待 Spike 验证"进入定案建议（裁决后改 Accepted）。
- EC-03 随机数行语义由本 ADR 落实：全局种子 + RNG 协议版本为必存字段；纯派生流零状态。
- 2.9 确定性边界第 8 条（玩家命令记录）与派生模式兼容：命令重放时事件键一致 → 随机结果一致。
- 系统命名空间注册表（namespace → 系统清单）随 decision-log 债务 #15 一起定案；命名空间一旦发布不得复用（版本 bump 视同协议变更）。

## 验证方法

- spikes/rng-spike 9 测试（隔离×2、调度无关、黄金复现、版本钉死、存档差异、算法冒烟、性能冒烟）。
- 黄金值测试（reproducibility_golden）进入 EC-11 黄金测试基线，不得自动覆盖。
- 跨平台黄金值复验列 R4（发布前）。

## 证据范围声明

原型与数据为单机实测（rustc 1.100.0，x86_64-pc-windows-msvc）；速度为非正式冒烟基准（docs/benchmarks/rng-algo-comparison.txt）；统计质量仅做冒烟（无 TestU01/PractRand 级测试）；跨平台一致性未验证（R4）。
